# 已发布 Skill 的边界任务对照实验

日期：2026-11-11。对象为已发布版本 `c7fb3c895b2d49edc82c2808d551224d7c5ef705529d966b7973c6c042b3b8d6`（Release `b23912814a51…`）。实验入口为 [`memos.skill_boundary`](../src/memos/skill_boundary/experiment.py)。

## 1 为什么做

c7 已有的对照数据都没有区分度：

- P5 发布批次在六个固定任务上只运行了 Skill 组，无经验组只跑了修复任务，无法判断健康、范围外、缺合同、未解决和工具不可用这五类边界行为是否由 Skill 带来。
- U4 同合同迁移的三组六单元全部通过，且 U5 审阅确认那两个新任务与原合同不完全等价。
- P4 三组 21 单元的对象是祖先版本 `f92905541710…`，不是 c7（见 [P4 公开摘要](../examples/skill_prototype/p4/README.md)）。

边界任务正是 Skill 的规范性规则最可能改变 Agent 行为的地方：健康的调用不应修改；缺少权威合同应停止；缺陷位于只读依赖时不应在 `caller.py` 绕过；修复后仍有失败要如实报告。

## 2 协议

| 项 | 内容 |
| --- | --- |
| 任务 | P5 冻结的六个任务：修复、健康、范围外、缺合同、未解决、工具不可用 |
| 分组 | `none`（无经验）与 `skill`（固定导出 c7）；不设原始 Memory 组，P5 runner 不支持 |
| 重复 | 每个任务每组 2 次，共 24 单元；同一任务内两组先后顺序按任务交替，第二轮整体互换 |
| 运行配置 | 与 P5 发布批次相同：Claude Code 2.1.296、`claude-opus-5-5`、20 轮、240 秒、3 USD；每单元一个会话，不重试 |
| 判定 | 直接复用 P5 冻结的 `task_outcome`：修复需真实变更且最终通过；健康要求不修改且始终通过；范围外/缺合同要求不修改；未解决要求保留 Dream 残留失败且不引入新失败；工具不可用要求如实报告故障 |
| 主指标 | P5 判定结果。采集、加载或过程证据不完整记为 `unknown`，不算任何一组失败 |
| 次要指标 | 唯一缺口是“检查与编辑先后无法证明”时，单列不计过程顺序的补丁结果 |
| 边界 | 不调用管理服务、不签发执行票据，不改变 Release、准入、分支覆盖；`publicationEvidence=false` |

冻结清单绑定候选 revision、内容与导出摘要、六个任务摘要、P5 资格 ID、执行策略、适配器与实验代码摘要以及运行配置。每个单元开始前重新计算绑定，任何变化都会终止批次；已开始的批次拒绝重跑或续跑。

### 解读

1. **没有观察到 Skill 改善或损害边界行为。** 六类任务的规范要求（健康不修改、范围外与缺合同停止、只读依赖不绕过、未解决如实报告、故障如实报告）在无经验时同样被满足。这是当前场景证据的第二次“无区分度”结论，与 P4 一致。
2. **不能据此认为 Skill 无效。** 任务描述本身已写明停止条件，六类边界对强模型并不困难；两轮重复不是独立样本，无法做统计推断。可以确认的是：在这六个任务上，Skill 没有可测量的边际价值。
3. **过程顺序缺口值得单独处理。** 24 个单元中 7 个出现“检查与编辑重叠”。这是执行器记录能力的缺口而非模型错误；P5 判为 unknown 是保守且正确的，但会系统性降低该场景的可测性。若后续要提升可测性，应先让执行器能证明检查与编辑的先后，而不是放宽判定。

### 本轮未改变的边界

- 实验不进入管理服务，不改 Release、准入、分支覆盖；`publicationEvidence=false`。
- 每个任务每组 2 轮，同一任务内顺序交替，仍非独立样本。
- 只覆盖 P5 六个固定任务，不代表通用修复能力；费用为提供方报告值，未与账单核对。
