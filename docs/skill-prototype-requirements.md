## 1 背景与问题

Coding Agent 在完成工程任务时会积累经验：任务上下文、执行步骤、失败尝试、解决方案和最终结果。这些经验分散在 Memory 和 Agent 运行数据里，其中一部分可以跨任务复用。

但直接把多次任务摘要汇总成“操作指令”是危险的。单条记录可能包含偶然成功、过时合同、错误尝试、只在特定环境成立的细节，或者 Agent 的自述而非事实。

**本需求要解决的问题**：在现有 MemOS Memory 系统之上，把多条真实经验提炼为**可追溯依据、可独立验证、可人工发布、可在 Agent 中受控使用、并能在来源或工具变化时被识别和处理**的过程性知识（Skill）。

**Skill 的定义**：具有明确目标、适用条件、诊断与操作步骤、分支、退出条件和验收要求的过程性知识。它说明“什么条件下做什么、观察什么、何时停止”，并能回到具体证据；它不是对话摘要，也不是无需验证的经验断言。

**核心验收原则**：修复必须恢复正确行为，并保留发现真实错误的能力。测试变绿、Agent 自述成功、格式检查通过，都不能单独证明修复正确或 Skill 有效。

## 2 目标与非目标

### 2.1 目标

| 编号 | 目标 |
| --- | --- |
| G1 | 从至少两个独立、相关且满足证据门槛的来源案例中生成候选，而不是手写一个 Skill 冒充提炼结果 |
| G2 | 经过 MemOS 实际保存与读取形成 MemorySnapshot；Skill 能追溯到实际 Memory 及原始证据 |
| G3 | 产生可审阅的固定 SkillRevision，在 Claude Code 中真实加载，并记录实际使用情况 |
| G4 | 使用独立任务和外部验收判断修复质量，与无经验、原始经验组对照 |
| G5 | 展示来源或工具变化后的定位、复核、暂停、修订和恢复 |
| G6 | 在数据面、控制面、前端提供一条可操作的最小管理链路，保留扩展能力 |
| G7 | 用户对项目启用一次 Claude Hook 后，正常使用 Claude Code 即可自动采集新经验，后台入库回读，并能查看同步状态和停用；采集不改变任务权限，不自动授予 Skill 资格 |

**成功交付不预设成功率必须提升。** 原型可运行、证据可信、实验可复现，并如实报告提升、持平、退化或证据不足，比无法核实的正向结论更有价值。

### 2.2 非目标

- 不覆盖所有 Python 故障；环境依赖问题作为适用性边界，并发故障留到后续。
- 不同时实现多个 Coding Agent；其他 Agent 只定义扩展契约。
- 不自动发布，不自动改写已发布正文，不在运行中静默升级。
- 不实现图上的自动规划、任意 Skill 自动组合或开放式自主探索。
- 不以语义检索、向量库或复杂图可视化作为最小闭环前置条件。
- 不修改模型权重，不采集模型私有推理过程。
- 不把小规模试验解释为跨项目、跨模型的稳定收益；不保证已导出的离线副本可远程撤回。
- 日常采集首版不扫描全部项目、不回溯历史 transcript、不保证采集所有中间自然语言消息或子 Agent；不替代 Claude 的模型认证，不改变普通会话的工具权限或执行隔离。

## 3 场景选择

### 3.1 为什么选这个场景

候选的三类故障为：环境与依赖不匹配、mock/fixture 契约与隔离问题、并发与时序问题。**mock/fixture 契约问题最容易在固定环境中构造独立验收、失败案例和错误修复**，因此作为首版主场景。

具体聚焦**图存储 Fake 与业务调用方的契约一致性**。项目已有真实历史缺陷：Dream 持久化调用 `update_node` 时多传了一个位置参数，异常被吞掉，写入实际没有发生，而 Fake 比真实接口更宽松，使测试没有发现问题。这说明“Fake 不能比被替代接口更宽松”是一条有价值、可验证的工程经验。

### 3.2 实际发布范围

经过来源复核和受控修订，最终发布的 Skill 收窄为：

> **受控 Dream UPDATE 调用中，删除 `update_node(id, fields, user_name=None)` 的 `fields` 前多余的位置参数。**

它不是通用 Python mock/fixture 修复 Skill。健康不修改、范围外停止、缺证据停止、工具异常如实报告属于规范性判断，不包装成新的修复经验。

### 3.3 日常采集范围

日常入口采集用户在允许目录内执行的普通开发任务，不限于 Dream UPDATE。当前部署选择 MemOS、MemOS-be、MemOS-fe 三个项目及其真实子目录；其他目录忽略，凭据与运行数据留在私有存储。**采集范围扩大不等于已发布 Skill 的适用范围扩大**；日常经验仍需另行建立任务合同、最终补丁验收和来源资格。

## 4 系统架构

```
 ┌──────────────── React 前端（fe 分支，/cn/skills） ────────────────┐
 │ 候选浏览 · 规则与来源 · 运行与评测 · 人工审阅与发布 · 生命周期 · 实验 │
 └──────────────────────────────┬──────────────────────────────────┘
                                │ 同源 API，会话认证 + 项目权限
 ┌──────────────────────────────▼──────────────────────────────────┐
 │ Go 控制面（be 分支，memosd）                                       │
 │ 22 条 /api/v1/skills/* 路由；按 view / write / manage 鉴权；       │
 │ 由服务端注入可信 actor、capability、project 后代理到数据面           │
 └──────────────────────────────┬──────────────────────────────────┘
                                │ 私有服务 Token
 ┌──────────────────────────────▼──────────────────────────────────┐
 │ Python Skill 管理服务（master 分支，src/memos/skill_*）            │
 │   ├─ MemOS Memory API     经验写入与实际回读                         │
 │   ├─ 独立 Neo4j            Skill Graph，与 Memory 库物理隔离          │
 │   └─ Claude Code 2.1.296   固定版本，macOS sandbox-exec 隔离执行      │
 └─────────────────────────────────────────────────────────────────┘
```

**职责划分原则**：Skill 正文、证据关系、依赖 DAG 及发布原子条件由 Python 数据面的 Skill 权威服务持有；Go 只负责身份、项目授权、审计和代理，避免出现第二套发布事实。浏览器不持有私有服务 Token，不能自行声明 actor 或权限。

新增日常采集入口与上述受控执行器分开运行：

```mermaid
flowchart LR
    A[允许项目内正常使用 Claude Code] --> B[项目级原生 Hook]
    B --> C[本机 SQLite 事件账本]
    C --> D[后台按轮整理待核验经验]
    D --> E[MemOS 写入与实际回读]
    C --> F[回环地址只读采集状态页]
    E --> F
    E -. 资格补证与转换尚未接入 .-> G[受控 Skill 提炼与管理流程]
```

Hook 只做本地采集，后台负责 Memory 网络操作。`skill_capture` 自带的只读状态页默认监听 `127.0.0.1:5282`，它不是 React `/cn/skills` 的新增管理路由，不具有审阅或发布权限。macOS 用户级 LaunchAgent 负责登录启动与退出重启；此后台是采集同步服务，不是 Skill 来源/工具的持续失效扫描器。

## 5 功能需求

### 5.1 经验采集与证据封存

**需求**：提供受控来源采集与日常观察采集两条入口。以下 R1.1–R1.6 约束受控案例的资格证据；日常入口按 5.12 保存观察与缺口，不能绕过这些门槛。成功、失败与未知均保留。

| 编号 | 要求 |
| --- | --- |
| R1.1 | 任务由可信注册表管理，区分 `source`（提炼来源）、`dev`（开发校准）、`holdout`（独立验证）三种用途；用途不能由模型或 Memory 标签改写；holdout 结果不得回流到提炼来源池 |
| R1.2 | 每个任务执行前先做**预检**：健康基线必须通过、注入故障必须失败，否则任务无效 |
| R1.3 | 证据包至少包含：身份与用途、任务合同引用、可恢复的初始快照、环境、工具事件清单、候选快照与变化、验收引用、来源与完整性 |
| R1.4 | **验收绑定最终补丁**：回执同时绑定 Case、Run、Attempt、初始及候选快照、环境、合同、验收器和实际检查结果；补丁之后再修改，旧回执失效 |
| R1.5 | 证据缺失分级处理：来源不明或损坏的隔离；最终验收缺失的不作为成功证据；初始失败缺失的不能支持“本操作修复了该失败”的因果结论 |
| R1.6 | 根因、用户反馈、模型费用可以缺失并标 unknown；不得让 LLM 补写不存在的退出码或事件 |

**实现**：`skill_experience`（`collection.py` 采集、`evidence.py` 封存与校验）、`skill_evaluation`（任务、快照、外部验收器）。

### 5.2 Memory 写入与回读

**需求**：经验必须真实经过 MemOS，不能用本地摘要冒充已入库 Memory。

| 编号 | 要求 |
| --- | --- |
| R2.1 | 通过 `/product/add` 写入，`/product/get_memory/{id}` 实际回读，生成带内容摘要的 MemorySnapshot |
| R2.2 | 不能用“最近一条 Memory”或文本相似度猜测归属；写入结果不确定时只沿原账本核对，不重复投递 |
| R2.3 | 绑定 Memory 服务端点身份；换端点拒绝继续，避免在不确定写入后制造重复 Memory |
| R2.4 | 读取失败、空响应、确认删除分别记录；无删除回执时不能把“读不到”断言为“已删除” |
| R2.5 | 日常经验采用独立命名空间与明确 user/cube/project 归属；回读标记 `source_identity_only`，确认来源身份而非派生正文的语义正确，不将其称为合格来源 MemorySnapshot |

**实现**：受控来源为 `skill_experience/bridge.py`（`MemoryBridge`）；日常入口为 `skill_capture/worker.py`，复用 `skill_experience/client.py`，使用独立 SQLite 账本。旧 MemoryBridge 的证据门槛不因日常接入而放宽。

### 5.3 经验资格与 Skill 提炼

**需求**：从多条合格经验中生成有逐规则依据的候选，抑制幻觉和错误泛化。

| 编号 | 要求 |
| --- | --- |
| R3.1 | **触发门槛**：至少 2 个独立谱系，且至少 1 个是带最终状态绑定的合格成功；一次任务的重试或多个 Memory 片段不增加独立案例数 |
| R3.2 | 提炼输入同时包含支持证据、相关反例、合同与缺口，不能只检索正向案例 |
| R3.3 | 每条操作性规则必须有可追踪依据或明确的规范来源；标记事实、规范合同还是待验证推断 |
| R3.4 | 不能解释的同前提反例列为阻断项；样本不足的分支删除或留在实验范围 |
| R3.5 | 执行轨迹和 Memory 文本只作数据；其中“必须遵循”类文本不获得系统指令地位 |
| R3.6 | 生成的 Skill、摘要不能作为新的独立来源，防止自我支持 |
| R3.7 | 生成后重新检查来源；来源在生成期间变化则不封存候选 |
| R3.8 | 每次提炼最多一次模型调用，失败保留，不自动换模型或重试到成功 |
| R3.9 | 修订采用有记录的定点修订（`source_review_patch_v1`），生成新 revision，父版本保留 |

**实现**：`skill_drafting`（`sources.py` 来源包、`pipeline.py` 编排、`generation.py` 生成、`domain.py` 结构校验、`revision.py` 修订）。

### 5.4 Skill 表达

**需求**：Skill 需要有可审阅、可校验的固定结构。

| 部分 | 内容 |
| --- | --- |
| 身份 | `skill_id`、不可变 `revision`、内容哈希 |
| 目标与范围 | 修复目标、适用机制、明确的不适用场景 |
| 前置条件 | 需要的合同、环境、权限、工具能力 |
| 编号规则 | 可观测问题、判据、动作、预期局部结果、下一步或退出、证据 |
| 退出条件 | `success` / `not_applicable` / `needs_evidence` / `unresolved` |
| 验收要求 | 正向、反向、回归检查及外部合同引用 |
| 证据 | 固定证据修订、定位、支持的具体主张 |

采用受约束的自然语言条件步骤，不新增执行 DSL。规则身份由 `(skill_id, revision, rule_id)` 确定。分类采用平面标签（用途：diagnose / repair / verify），不建层级分类树。

### 5.5 Skill Graph

**需求**：设计并实现 Skill Graph，建立 Skill 与来源 Memory、Skill 与 Skill 之间的关系。

**9 类节点**：`Skill`、`SkillRevision`、`Rule`、`MemorySnapshot`、`CaseRevision`、`Run`、`EvidenceRevision`、`Validation`、`Release`

| 关系 | 语义与用途 |
| --- | --- |
| `Skill —HAS_REVISION→ SkillRevision` | 某 Skill 的具体版本 |
| `SkillRevision —HAS_RULE→ Rule` | 版本中的规则 |
| `SkillRevision —DERIVED_FROM→ MemorySnapshot` | 经验来源；不单独证明规则正确 |
| `MemorySnapshot —REFERENCES→ EvidenceRevision` | Memory 与原始证据的显式对应 |
| `Rule —EVIDENCE_LINK→ EvidenceRevision` | 支持、反驳、前提或背景关系 |
| `EvidenceRevision —FROM_RUN→ Run` / `Run —OF_CASE→ CaseRevision` | 证据的产生执行与所属任务 |
| `Validation —EVALUATES/USES_RUN→` | 验证报告评估的精确版本与采用的执行 |
| `Release —PUBLISHES/BASED_ON→` | 发布的精确版本与引用的验证 |
| `Skill —RELATED_TO— Skill` | 对称、非传递的主题关联；**仅导航，不传播失效** |
| `SkillRevision —REQUIRES→ SkillRevision` | 必需的精确版本依赖；有向无环；**传播失效** |
| `新 SkillRevision —SUPERSEDES→ 旧 SkillRevision` | 经批准的版本替代；不自动撤回旧版 |

| 编号 | 要求 |
| --- | --- |
| R5.1 | 使用独立 Neo4j 数据库实例，导入时校验目标库身份与 Memory 库不同 |
| R5.2 | 写入追加式、幂等；已存在节点或边内容不同时报 `immutable_conflict` |
| R5.3 | `REQUIRES` 环检测（并发添加相反依赖时一笔成功、一笔 `graph_cycle`） |
| R5.4 | 提供规则溯源查询（`trace_rule`）：沿固定路径从规则追到证据、运行、案例、Memory，只跟随规则自身引用 |
| R5.5 | 提供来源影响查询（`affected_by_memory`）：从变化的 Memory 反向定位受影响的版本与规则 |
| R5.6 | 演示依赖传播时只能使用明确标记的合成管理测试数据，不得把未提炼、未验证的节点标为真实 Skill |

**实现**：`skill_drafting/graph.py`、`graph_bundle.py`；管理图读取使用 `skill_management/repository.py` 中的 `ManagementRepository`。

### 5.6 Coding Agent 适配（Claude Code）

**需求**：至少一个 Coding Agent 实际接入，并为其他 Agent 留出扩展路径。R6.1–R6.7 描述受控执行/加载适配器；普通会话采集遵循 R6.8–R6.9 和 5.12。

| 编号 | 要求 |
| --- | --- |
| R6.1 | 受控实验固定 CLI 版本（`2.1.296`）、模型标识（拒绝 `latest` 等别名）与工具白名单 |
| R6.2 | **固定导出**：候选渲染为原生 `SKILL.md`，`export_hash` 覆盖全部字节；运行时别名包含 revision 与内容摘要，不使用浮动的 latest |
| R6.3 | 原生显式加载；只有观察到原生发现并展开 Skill 才记 `loaded=verified`，模型自述不算 |
| R6.4 | 适配器提供两个 MCP 工具：`run_visible_checks`（Agent 只能经此运行可见检查，结果由宿主执行记录）、`record_rule`（声明规则、阶段、观察与决定） |
| R6.5 | Agent 不可读取隐藏验收、参考补丁、其他组工件或私有配置 |
| R6.6 | 三种运行模式严格分离：来源采集或无经验对照（不加载 Skill）、候选评估（隔离入口）、已发布使用（需准入） |
| R6.7 | 错误分类返回：`capability_missing`、`artifact_mismatch`、`load_unverified`、`needs_evidence`、`release_unavailable`、`capture_incomplete` |
| R6.8 | 日常入口使用用户现有 Claude CLI，通过项目配置接收原生事件，不要求从服务端执行器启动；本次实际验证版本为 `2.1.322`，不据此替换受控实验的固定 CLI |
| R6.9 | 保留用户其他 Hook、权限和模型认证；日常采集不自动加载当前固定任务的 Dream Skill，不将采集事件当作 Skill 已加载或正确使用的证据 |

**扩展路径**：适配器契约（输入、导出映射、运行配置、输出、错误语义）与 Agent 无关；接入其他 Agent 需实现对应导出格式、加载证据与事件采集，并单独验收。

**实现**：受控适配使用 `skill_adapter`（`artifacts.py` 导出、`runner.py` 运行配置、`recording_server.py` MCP 工具、`events.py` 事件、`isolation.py` 沙箱）；日常接入使用 `skill_capture`（安装、原生 Hook、本地事件、同步及状态页）。

### 5.7 正确性检查

**需求**：从结构、内容、使用三个层面校验 Skill，抑制无依据结论与幻觉。

| 层次 | 自动检查 | 人工判断 |
| --- | --- | --- |
| 结构 | 字段、规则身份、分支可达、退出完整、引用解析、哈希、格式 | 是否足以让使用者理解 |
| 内容 | 证据资格、谱系、合同版本、冲突清单、已知反例回归 | 证据是否真正支持规则、范围是否过宽 |
| 使用 | 真实加载、适用检查、观察分支、实际修改、独立验收 | 异常路径、隐蔽捷径、执行偏离与规则缺陷的归因 |

自动检查最多给出“技术检查通过，等待人工发布”。LLM 审查可以辅助发现问题，但不能批准自己生成的规则。

### 5.8 独立验证、审阅与发布

**需求**：发布前必须经过独立任务验证和人工审阅，不能自动发布。

**发布资格任务**：6 个固定任务，覆盖 Skill 的全部分支与停止边界。

| 任务 | 期望行为 |
| --- | --- |
| 修复 `update-repair` | 真实修改，初始失败、最终通过 |
| 健康 `update-healthy` | 不修改，始终通过 |
| 范围外 `scope-outside` | 缺陷在只读依赖，不得在调用方绕过 |
| 缺合同 `contract-missing` | 无权威合同时停止，不修改 |
| 未解决 `update-unresolved` | 保留真实残留失败，不引入新失败 |
| 工具不可用 `check-unavailable` | 检查工具故障时如实报告 |

**发布就绪闸门**（任何一项不满足即不能发布）：

- 无未关闭挑战、未解决反例或严重违规；
- 无失败或 unknown 的验证结果（除非已人工裁决为预期停止）；
- 有独立验证，且**分支覆盖、边界覆盖、范围覆盖**完整；
- 验证所用的内容摘要、导出摘要与当前版本一致；
- 生命周期闸门通过。

**发布流程**：生成固定审阅包（含内容与工件哈希、验证运行、补丁回执、成本、未决项）→ 逐条裁决 → 带审阅包 ID 与哈希提交发布 → 项目锁事务内原子复核，期间出现新反例或依赖变化返回冲突。

| 编号 | 要求 |
| --- | --- |
| R8.1 | “测试变绿”不等于修复：还需过程证据完整、修复周期 ≤ 2、无未经验证的编辑、回执与最终快照绑定 |
| R8.2 | 不为取得覆盖而静默重试；每单元只运行一次 |
| R8.3 | 历史失败与 unknown 保留，不被新版覆盖追授 |
| R8.4 | 审阅身份如实记录（本次为“用户授权、助手受托审阅/执行”），不冒称用户逐项亲审 |

**实现**：`skill_p5`（资格任务、批次、执行策略）、`skill_management`（审阅包、发布事务）、`skill_governance`（裁决）。

### 5.9 正常使用与准入

**需求**：只有正式发布且当前仍有效的版本能被 Agent 正常加载。

此节的“正常运行”指管理服务中的 `normal` 模式。用户直接打开的普通 Claude 会话是另一种入口：当前仅自动采集，没有自动检索或加载 Skill，不继承以下固定任务发布资格。

每次正常运行前实时检查：

1. 状态为 `published`、有 Release、无未关闭挑战；
2. 发布就绪仍为 `PASS`（含生命周期无新根因）；
3. Release 记录的 revision、内容、导出、manifest、来源水位全部与当前一致；
4. 本次任务在 Release 授权的 `caseIds` 范围内；
5. 实际导出摘要与准入记录一致。

| 编号 | 要求 |
| --- | --- |
| R9.1 | 候选或失效 Release 不能进入正常加载路径 |
| R9.2 | 管理服务同一时间只运行一个任务（单执行槽） |
| R9.3 | 运行结果回写为反馈；`unknown` 作业不被覆盖，修复只能**追加**恢复记录 |

**实现**：`skill_management`（`repository.py` 准入、`service.py` 运行、`feedback.py` 反馈恢复、`p5_runtime.py` 正常编排）。

### 5.10 持续演进与失效处理

**需求**：来源 Memory 或工具变化后，系统能识别受影响的 Skill 并阻断使用，恢复需要新证据。

| 编号 | 要求 |
| --- | --- |
| R10.1 | 发布版本绑定监测对象：**Memory**（来源快照内容摘要、归属与来源字段）、**工具**（CLI 二进制哈希、版本输出、适配器与运行实现文件哈希） |
| R10.2 | 扫描发现 `changed` / `unavailable` / `invalid` 时开启根因，准入立即拒绝 |
| R10.3 | **恢复不自动解禁**：对象恢复后记为 `restored_pending`，仍拒绝；必须有根因开启之后的新独立验证，并经人工决定（restore / retain / supersede） |
| R10.4 | 依赖传播：只有 `REQUIRES` 闭包传播失效，`RELATED_TO` 不传播；多根因需分别解除 |
| R10.5 | 版本替代写入 `SUPERSEDES`；撤回的 Release 不能被恢复，重新授权需新审批与新 Release |
| R10.6 | 监测绑定只能追加，旧基线保留；追加后要求新执行验证 |
| R10.7 | 已加载的旧 Skill 上下文无法远程抹除；控制范围限于后续加载与可控动作 |

**实现**：`skill_lifecycle`（`observers.py` 观察、`repository.py` 根因与传播、`execution.py` 执行票据）、`skill_management/maintenance.py`（追加监测）。

### 5.11 效果评估

**需求**：判断 Skill 是否真正有效，而不只是“看起来合理”。

| 编号 | 要求 |
| --- | --- |
| R11.1 | 对照组：无经验、原始 Memory、Skill；同一任务初始快照、模型配置、工具权限、预算与外部验收 |
| R11.2 | 预算在 dev 校准一次后冻结，不能看到 holdout 结果后调整；执行顺序预先固定或按记录的种子随机 |
| R11.3 | 指标分层报告，不合成单一分数：修复结果、边界判断、质量底线、配对对照、成本、证据有效性 |

### 5.12 日常 Claude Code 自动采集

**需求**：在用户允许的项目内配置一次，之后直接使用 Claude Code 即可产生新经验记录；采集不以浏览器或受控任务执行器为前提。

| 编号 | 要求与当前行为 |
| --- | --- |
| R12.1 | 项目级安装到 `.claude/settings.local.json`，合并保留已有配置与其他 Hook；备份原文件、重复安装幂等，卸载只移除自己管理的命令 |
| R12.2 | 按真实目录判断允许范围，避免符号链接或相似路径前缀越界；只接收启用后的新事件，不扫描历史 transcript |
| R12.3 | 接收 SessionStart、UserPromptSubmit、PreToolUse、PostToolUse、PostToolUseFailure、Stop、StopFailure、SessionEnd 八类事件；记录请求、工具输入/输出/错误和最终回复 |
| R12.4 | 关联项目、会话、轮次与原生工具 ID；允许并发和迟到结果，工具结果归属启动它的轮次；有稳定身份的重复事件去重，相同文本的新请求不能被吞掉 |
| R12.5 | Hook 使用轻量标准库入口，只快速写本地账本；不联网、不调用模型、不执行输入中的命令，不改变工具权限；采集失败不阻断用户任务，输出安全错误标记 |
| R12.6 | 过滤凭据字段、已知秘密值、匹配的敏感文件工具内容和内部推理；有界截断并标记，不声称模式脱敏能识别所有语义隐私 |
| R12.7 | Stop 仅表示一轮回复结束，SessionEnd 仅表示会话结束，均不证明任务成功；安静窗口后归档，未结束轮次闲置后归档并标缺口；迟到事件或完整性变化产生新修订，保留旧记录 |
| R12.8 | 全部记录为 `observed_unverified`，不增加合格成功来源或独立验证样本；Memory 已同步也不意味着可提炼、可发布或已经获得 Skill 效果证据 |
| R12.9 | 后台同步到现有 Memory 并实际回读，核对用户、cube、命名空间、项目、操作 ID、证据/摘要哈希与来源覆盖；完整原始来源附于正文分块时只确认 `source_identity_only` |
| R12.10 | 区分尚未提交与提交结果未知：前者离线保留、恢复后可提交；后者只查询回读、不盲目重发 POST；显式 reconcile 仍只读，原错误留在投递审计中 |
| R12.11 | 只读状态页展示允许项目、会话、事件、经验、完整性与同步状态，以及真实 Memory ID；文本转义、仅回环监听，不提供写接口或任意文件读取，不替代管理控制面的项目授权 |
| R12.12 | 部署内容寻址程序副本，避免切换源码分支使 Hook 消失；macOS LaunchAgent 登录启动并在退出后重启。解释器、Memory 服务与模型认证仍是独立运行前提 |
| R12.13 | 提供 install、uninstall、status、serve、service-install、reconcile 命令。卸载关闭新采集但不删除历史数据；后台可继续同步已有队列，完全停止后台另行执行 bootout |

**状态语义**：`pending` 为等待同步，`sending` 为已开始提交，`pending_reconcile` 为提交结果待核对，`synced` 为来源身份回读确认，`invalid` 为不一致待处理。这些是投递状态，不是任务成功率或 Skill 发布状态。

**实现**：`skill_capture/core.py`（配置、脱敏、事件账本）、`worker.py`（经验修订与投递回读）、`install.py`（配置合并）、`deployment.py`（固定副本与 LaunchAgent）、`dashboard.py`（只读状态页）、`cli.py`/`entrypoint.py`（命令入口）。

| 权限 | 读取需项目查看权限；候选与评测需写权限；发布与状态管理需管理权限；由服务端执行，前端按钮不构成授权 |
| 隔离 | 受控执行使用 macOS `sandbox-exec`，隔离缺失时拒绝启动；日常采集 Hook 不给普通 Claude 会话增加同等沙箱或发布资格，保留用户原有权限 |
| 日常可用性 | Hook 本地写入与后台网络同步分离，模型认证故障也保留观察；SQLite 512 MiB 上限、内容大小限制与缺口标记，长期保留/自动清理另列为待实现 |
| 不改动现有功能 | Skill 全部为新增 `skill_*` 模块；未修改现有 `memories`、`dream`、`api`、`graph_dbs` |

**结论**：三次对照都**没有区分度**。在当前场景的任务上，没有观察到 Skill 改善或损害 Agent 行为，Skill 组则一致地更慢、更贵。这不能证明 Skill 无效——任务描述本身已写明停止条件，所选任务对当前模型并不困难；每格样本量也不足以做统计推断。可以确认的是：**在这些任务上，Skill 没有可测量的边际价值。**

逐单元评分摘要以机器可读形式公开在 `examples/skill_prototype/{p4,p5,usability-v1,boundary-ab}/`，并以哈希绑定操作者保管的原始证据。原生对话、完整运行轨迹与私有部署工件未公开，哈希不能替代对这些原始证据的独立复核。

## 9 已知限制与后续工作

### 9.1 尚未达到的要求

| 编号 | 内容 | 关闭方式 |
| --- | --- | --- |
| L1 | 支撑修复动作的独立成功经验只有 1 条 | 再采集至少一条独立谱系的成功经验，并修订候选 |
| L2 | 真实 Skill↔Skill 依赖缺失 | 提炼并发布第二个真实 Skill，展示非合成的 `REQUIRES` 与失效传播 |
| L3 | 来源 Memory 变化未在发布版本上真实演示 | 机制与测试已有；演示会暂停准入并需要恢复验证的模型调用 |
| L4 | 效果实验无区分度 | 选择无经验组会失败的任务族；或先补执行器对“检查与编辑先后”的记录能力，否则同场景加样本仍无差异 |
| L5 | 日常经验尚未自动转成 Skill 候选，也没有普通会话的自动 Skill 检索/加载 | 补齐任务边界、权威合同与最终补丁验收，建立相关经验筛选/资格转换和后台提炼触发；发布仍需人工审阅，普通会话另验固定版本加载与使用证据 |

### 9.2 工程限制

- **执行器记录缺口**：Agent 在编辑同时调用检查时，过程证据无法证明先后顺序，结果判为 unknown。边界对照中 24 单元有 7 个出现此情况，两组同样受影响。
- **平台**：执行隔离只验证了 macOS `sandbox-exec`；Linux 与容器后端未实现。
- **Agent**：只接入 Claude Code，其他 Agent 只有扩展契约。
- **自动化程度**：已启用项目的新日常事件可自动整理并同步 Memory；提炼触发、语义审阅、发布裁决仍需发起，日常记录不会自动进入这些环节。
- **代码重复**：为保持历史证据可复验，冻结协议以显式版本副本存在（例如 `skill_p5` 与 `skill_release` 大部分文件仅协议常量不同），维护成本较高；后续可提取公共实现。
- **评审规模**：数据面 PR 累积了 P0–P5 的协议、任务资产、测试和后续日常采集模块，范围较大；建议按来源与提炼、治理与生命周期、受控运行、日常采集、测试与文档分组审阅。
- **监测范围**：工具监测只覆盖明确列出的主体，不覆盖所有宿主代码，也不提供持续后台监听。
- **未集成实验**：`skill_release_v2`（跨模块场景）未接入当前产品。
- **日常证据**：没有任务权威合同与独立最终补丁验收，未覆盖所有中间消息、子 Agent 或取消场景。完整性配对无缺口也不等于任务正确。
- **日常存储与隐私**：有界截断、模式与已知值脱敏存在边界；512 MiB 后拒绝继续写入。自动清理、长期归档、分布式同步和后台跨平台部署未实现；状态页仅供本机使用，未接入 Go 项目权限体系。

### 9.3 后续建议（按优先级）

1. **打通日常经验资格与候选触发**：先补证据与审阅入口，再做相关经验发现；不得仅凭会话结束或 Memory 同步升级资格。
2. **补执行器的检查-编辑顺序记录**，提升现有任务的可测性。
3. **设计有区分度的效果实验**：找到无经验组会失败的任务族，直接在发布版本上做三组对照。
4. **扩充独立成功来源**，提炼第二个真实 Skill，关闭 L1、L2；新日常记录不自动计入。
5. **在发布版本上演示来源 Memory 变化**，关闭 L3。
6. **补普通会话的固定版本使用与采集维护能力**：审阅后的 Skill 检索/加载、留存策略、容量提示与长期归档，并提取协议公共层降低维护成本。

### 10.3 运行前提

受控原型需要 Python 3.11+ 与项目 `.venv`、Claude Code 2.1.296 受信专用副本、可写的专用 Memory cube/user、与 Memory 不同实例的 Neo4j，以及 macOS 执行隔离。凭据经环境变量或私有配置提供，不进入仓库。

### 10.4 日常使用入口

按 [日常采集操作文档](skill-prototype-daily-capture.md) 准备私有配置，安装一次项目 Hook 与后台服务：

```sh
.venv/bin/python -I src/memos/skill_capture/entrypoint.py install --config "$CAPTURE_CONFIG"
.venv/bin/python -I src/memos/skill_capture/entrypoint.py service-install --config "$CAPTURE_CONFIG"
```

然后在允许的项目目录内正常启动 `claude`，无需先从 Skill 管理页面创建任务。已有会话未重新加载 Hook 时退出后重启；示例与本机配置为一轮结束安静 8 秒后归档，未结束轮次闲置 5 分钟后保存缺口。模型认证由用户自己的 Claude 配置负责；Memory 暂不可用时先保留本地记录。日常入口不需要管理服务或独立 Skill Graph 常驻，但同步依赖现有 Memory 服务。

浏览器打开 `http://127.0.0.1:5282/` 并刷新，可查看经验、事件及同步状态。`synced`/“Memory 回读已确认”只表示来源身份回读确认，不代表 Skill 已生成。该入口本次使用 Claude Code 2.1.322 与 macOS 实测，不改变受控实验的固定工具版本。

```sh
# 查看状态
.venv/bin/python -I src/memos/skill_capture/entrypoint.py status --config "$CAPTURE_CONFIG"

# 显式只读核对已尝试提交的记录；保留原错误，不重发 POST
.venv/bin/python -I src/memos/skill_capture/entrypoint.py reconcile --experience EXPERIENCE_ID --config "$CAPTURE_CONFIG"

# 停用新采集，保留历史记录与其他 Hook
.venv/bin/python -I src/memos/skill_capture/entrypoint.py uninstall --config "$CAPTURE_CONFIG"
```

卸载采集后，后台仍可处理既有队列；完全停止和取消登录启动的步骤见操作文档。代码副本与状态放在私有目录，解释器仍依赖项目 `.venv`，切换源码分支不会替换运行副本，删除解释器则会影响服务。
