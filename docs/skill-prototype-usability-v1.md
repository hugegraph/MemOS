# Skill 本机可用性优化开发计划

日期：2026-11-11。基于已交付 P5 的三个分支创建 `codex/skill-usability-v1`、`codex/skill-usability-v1-be`、`codex/skill-usability-v1-fe`。本轮在本机开发与提交，仍限于 Dream UPDATE 合同修复。旧 Skill、Release、来源及批次保持不可变；改动不追授旧记录资格。

## 开发顺序与验收

| 工作包 | 功能 | 必须通过的验收 |
| --- | --- | --- |
| U1 扩大变化监测 | 宿主显式追加正常编排器及管理执行相关代码的固定监测项；版本化绑定历史 | 未暂停不能升级；旧主体不可删改；重复操作幂等；升级后保持暂停，旧验证不能恢复；改动被监测文件实际变为 changed，恢复字节仍需新证据 |
| U2 服务内正常作业 | `POST /api/v1/skills/runs/start`，服务器固定 normal；网页增加正式运行操作，复用现有唯一执行槽、轮询和作业审计 | 未发布/失效/范围外拒绝；只读用户不可启动；不能传 mode、命令或路径；相同 operation 不重复启动；与评测共用忙碌限制；服务运行期间能启动并回收真实 Claude 作业 |
| U3 反馈恢复与显示 | 对 unknown 作业的已完成宿主工件重新验读并追加恢复记录；保留原作业状态，网页显示原始失败、恢复结果和验证关联 | 不接受客户端报告或文件路径；不能重跑模型；绑定原作业/候选/导出/票据/最终补丁；缺失或篡改证据拒绝；重复恢复幂等；恢复不产生独立分支覆盖 |
| U4 新独立任务 | 在当前 Skill 已冻结之后构造小规模未向执行模型公开的新验证任务，固定合同、预算、评分和分组后执行 | 隔离自检区分初始故障、正确修复和弱化检查；与来源任务不重复；无经验/原始 Memory/Skill 使用同任务同预算；失败和成本全部保留，不依据结果改题或重试到成功 |

每包先补针对真实风险的失败测试，再实现，完成相应检查后中文提交。U1–U3 先完成，再冻结 U4 的具体任务和执行协议，不把测试数量或派生变化当作泛化证据。

## U1 绑定升级合同

新增宿主专用 `extend_lifecycle` 事务，只接受当前固定候选处于 paused、正确 expectedSequence、原 bindingId 和新增完整主体；所有原主体逐字保留。新 binding 引用原 binding，旧记录不改。追加监测项不伪造工具变化观察，未扫描的新主体保持 unavailable。升级推进执行水位，刷新暂停时已有验证集合；只有升级后新执行、当前观察一致并被裁决合格的独立验证才能恢复。

迁移入口由本机运维脚本完成，使用配置和受信代码生成监测清单；浏览器不能上传监测路径、预期摘要或替换旧基线。迁移需独占管理服务锁，避免修改正在执行的宿主绑定。正常使用不再需要停止服务；绑定迁移属于低频维护操作。完成实现与测试后才冻结新清单，后续改动需新维护周期。

## U2 与 U3 接口约束

正常执行复用 `SkillService.start(mode="normal")`，在开始和结束均使用真实来源/工具扫描与发布准入；返回现有 SkillJob，不扩大任务白名单。网页的准入预览不构成授权，启动时仍由服务器复验。开始操作不自动重试，轮询只访问查询接口。

反馈恢复使用 `jobs/reconcile` 管理权限入口，只接收 projectId/jobId/operationId。宿主从自己的 artifactsRoot 和图中作业身份解析工件；不能把用户提供的 JSON 当作验收。恢复结果单独保存，原 unknown 不修改；正常反馈仍为 isolated_dev、空分支覆盖。页面按运行时间显示最新作业，清楚区分原状态和追加反馈。

## 范围、验证环境与限制

继续使用既有 Memory、独立 Skill Neo4j、Claude CLI 专用副本及前端；私有配置、服务日志和运行工件留在仓库外。按三个项目 README/CONTRIBUTING 执行 Python 定向及必要回归、Go `make check`、前端 `pnpm verify`，并在真实浏览器展示新操作与恢复记录。

不扩展新的修复场景、不自动发布、不改变历史数据来换取通过。U4 的任务由开发者编写并知晓，只能称执行模型未预先接触的验证，不能宣称开发者双盲。小样本结果用于发现误用与成本问题，不预设 Skill 有收益；没有满足证据门槛的结果应如实保留。

## U4 执行前协议

继续限于 Dream UPDATE 多余位置参数缺陷，新增两个任务实例，不把它们算作新的问题族。T1 把 UPDATE 放在批量计划处理中，包含跳过无内容条目和其他操作；T2 把 UPDATE 放在带版本检查的操作中，包含空字符串与版本不匹配边界。两者均给出权威 `update_node(id, fields, user_name=cube)` 合同，正确修复只需删除多余位置参数，不能修改假数据库、公开检查或跳过写入。两者不用于提炼或修改当前 Skill。

每题固定 none / raw_memory / skill 三组，各运行一次，共六次；顺序 T1 none→raw_memory→skill，T2 skill→raw_memory→none。使用同一 CLI 摘要、模型、20 轮、240 秒、3 USD 上限、工具集合。运行前冻结任务正文、独立判据、Skill 导出、原始 Memory、执行器和自检摘要；原始 Memory 从已回读的固定来源快照取得，保留原文，不另写解题摘要。所有组获得相同公开检查与规则记录能力。

自检需确认：初始版本失败、参考补丁通过、跳过写入和放宽假数据库均不通过、删除检查及新增文件被拒绝。实际执行采用操作系统隔离；Agent 不能读隐藏判据、参考补丁或其他组。每次结束对封存的最终补丁在无网络、无凭据环境运行隐藏判据，收据绑定任务和快照摘要。模型预算耗尽、退出异常、加载未证实分别记录为未知；行为检查失败记录失败，不通过重试改变结果。

指标分别报告行为通过、采集/加载、公开检查、耗时和全部报告费用。规则声明不自动等于正确使用。六次结果不产生发布资格，不扩大当前 Release 的 caseIds，不进入来源 Memory，不做显著性或泛化收益结论。这里的“独立”指任务与来源实例分开、最终验收由宿主实施，仍存在同一开发者知晓 Skill 与任务设计的偏差。
