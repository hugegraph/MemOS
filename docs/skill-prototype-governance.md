# P4 后续：人工裁决、分支覆盖与变更传播开发合同

日期：2026-11-09。前置为 [P4.1](skill-prototype-p41.md) 的实际验收。本文先冻结 42-A/B 的实现边界，实际进度另见第 9 节；接口完成不表示人工裁决或新版发布已经完成。

## 1 当前事实与交付目标

原 P4 的 21 次运行与评分保持冻结。H4 的三次补丁可以用 P4.1 单独复验，新增观察不能覆盖原 unknown，也不增加独立样本数。H6 的合理停止必须由人依据完整过程判断，不能把没有修复当作修复成功。候选目前是 MemOS scoped `get_node` / Dream `update_node` 专用过程，共六条规则、22 个分支；七个 transfer holdout 不证明这些专用修复分支。

42-A 交付：可信证据登记、固定裁决包、追加人工裁决、逐分支覆盖矩阵和有效资格计算。42-B 交付：来源/工具变化观察、按固定依赖传播的影响记录、恢复/撤回/替代事务与加载准入。P5 才执行综合闭环演示。不得以合成测试记录、人类批准按钮测试或资产 reference 运行代替真实发布证据。

## 2 数据和信任边界

继续使用独立 Neo4j Skill Graph 和项目级事务锁，不新增数据库。原 Candidate、Validation、Release 与来源快照不可变。内部管理记录增加不可变类别，记录内容摘要与项目范围；只有状态投影允许更新。下述关联使用精确 ID，不接受名称近似匹配。

| 记录 | 必需绑定 | 用途 |
| --- | --- | --- |
| EvidenceAssessment | validationId、原报告/事件/凭条摘要、最终快照、验收协议、task/lineage、候选/导出、观察类型、受信生成器版本 | 宿主读取和复核工件后登记的证据；不是 HTTP 自报通过 |
| AdjudicationPackage | 候选/导出、sequence、EvidenceAssessment IDs、原 validation IDs、来源水位、规则/分支定义、待判项、创建人 | 固定本次人真正看到和判断的内容 |
| Adjudication | 精确包 ID/hash、actor、reason、逐项决定、引用事件与检查、时间、operationId | 追加人工判断，不能改写原记录或移除失败日志 |
| ImpactObservation | 观察对象及固定版本、预期/实测摘要、检查器版本、changed/unavailable/restored、关联前一观察 | 来源/工具变化事实；连接失败与已证实变化分开 |
| ImpactDecision | 根因 ID、受影响版本/依赖路径、阻断/恢复判断及依据、actor、时间 | 解释当前为何不可用；多个根因分别保留 |

服务端 EvidenceAssessment 的入口为宿主命令或受信后台注册，不能从浏览器传路径、命令、完整验收报告或 `passed`。受信入口也必须实际回读快照与凭条，限制注册目录和大小，绑定完整事件链；不把文件名或单独哈希当作验收证明。缺少原工件的历史项只能登记 `evidence_unavailable`。

前端通过 Go 的项目会话与角色授权调用 Python；actor 来自会话，不能由请求正文指定。查看需要 view，裁决/挑战处置/恢复/发布需要 manage。自动检测使用明确的系统 actor，不声称为人类。私有路径、凭据与完整运行工作区不进入公开响应。

## 3 裁决和覆盖的最小合同

每个待审项只能选择相应类别的决定，且必须填写理由。分开记录：

1. **任务结果**：修复成立、合理停止、真实失败、证据不足；修复成立必须有与最终补丁绑定的可信验收，合理停止不增加修复成功分子。
2. **历史异常处置**：验收基础设施异常已解释、证据仍不足、反例成立。解释异常要引用同一最终补丁的新协议复验；历史 unknown 和旧评分仍保留。
3. **规则使用**：正确使用、误用、未使用、不可判断；声明与事件不一致不能记为正确使用。
4. **分支覆盖**：精确 `rule_id#index`、条件成立的观察、实际行动/退出的事件、结果检查。仅声明规则、结果碰巧通过、source/dev 重用或与前提无关的任务均不计覆盖。

人工可以判断语义，不能豁免摘要错误、缺失凭条、来源/独立任务重叠、禁止行为或不完整采集。反例/误用需要明确适用范围；范围外任务不应自动推翻范围内规则，但不能贡献其修复分支。

有效资格是原始事实与追加裁决的投影，不是修改原 `Validation.status`：历史异常被解释后只解除对应 `validation_unknown` 原因；任何开放挑战、独立验证缺口、分支缺口、来源变化、依赖失效仍阻断。新的互相矛盾裁决产生待审冲突，不能按最后一条静默覆盖。纠正旧裁决必须显式引用被纠正记录，并绑定新包和当前 sequence。

审阅包加入裁决与影响记录 IDs；任一新增证据、挑战、裁决或影响都递增 sequence，使旧包失效。操作 ID 幂等，重复同一请求返回原结果，复用 ID 改正文返回冲突。裁决和投影更新在一次事务内完成。

## 4 独立覆盖任务的编排原则

先根据当前 22 个分支创建待覆盖矩阵，再登记新任务与锁。每项包含目标条件、允许行动、可观察检查、正例、保留错误检测的反例、来源谱系审查。任务先冻结后交给 Agent；不能用已见失败后的临时修改算原任务通过。

| 分支族 | 任务方向 | 验收重点 |
| --- | --- | --- |
| scoped read 修复/复验 | 独立编写的多租户读取合同，含合法无范围读取与错误类型/跨租户输入 | 同时保留合法调用和拒绝能力，不复用 source 补丁或改名代码 |
| Dream UPDATE 修复/复验 | 独立编写的更新动作及有状态 fake，覆盖调用参数、返回与无意写入 | 校验实际参数和副作用，不能通过宽松 fake 隐藏调用方错误 |
| 两类合同组合 | 同一任务中明确不同缺陷与修复预算 | 只覆盖实际进入的顺序，不能由单独两题推出组合路径 |
| already correct / not applicable | 已正确实现、明确范围外合同 | 保持文件不变并给出正确依据，不能奖励无关修复 |
| needs evidence / unresolved | 明确缺失的合同/检查输出、冲突或超出支持范围的失败 | 保留失败，指出缺什么或停止原因；不得发明约定或绕过检查 |
| 两周期限制 | 可重现而支持规则不能解决的任务 | 保留完整时间顺序与修复/复验计数，不能伪造调用记录 |

一项任务可能覆盖多个分支，但每个分支都需要独立的事件证据。覆盖不足时追加预先冻结的任务批次，不重标旧 source/dev，也不把新任务混入原 21 次固定效果实验。若某条规则没有来源支持或其条件无法可靠观察，修订候选并重新验证，不能仅删除验收项来满足门槛。

固定三组效果对照和分支验证用途分开：分支任务检查过程正确性，不能以其挑选后的成绩宣称总体收益。耗时/成本保留真实支出；合理停止、基础设施失败、任务失败分栏统计。

## 5 变化检测与传播

Memory 检查用实际回读的内容/元数据语义摘要比较冻结来源；网络错误为 unavailable，不冒充内容变化。工具能力清单固定 Agent/CLI 版本、工具名称、参数 schema、返回/错误约定与受信行为探针版本。名称、参数或实现摘要变化触发检查；仅凭版本号相同不能证明行为相同。

自动检查在新评测、审阅准备、发布、normal 加载及任务结束时执行。可提供显式管理员扫描，不在本轮增加无人值守调度。检查不可用时拒绝新 normal 加载；已经开始的任务记录结束时准入变化，不能承诺撤销已进入模型上下文的内容或逐工具调用实时拦截。

传播按项目内固定版本拓扑计算：

- 来源变更 → 引用该 MemorySnapshot 的 Rule/SkillRevision。保留变更前后摘要及相关规则。
- 工具变化 → 依赖对应能力清单的版本。
- 必选 `REQUIRES` → 反向传递到依赖者，记录根因和完整依赖路径；循环或缺失版本拒绝。
- `RELATED_TO` 不传播；`SUPERSEDES` 仅表达替代建议，不自动重绑定 `REQUIRES` 或已冻结运行。

一个版本可以有多个阻断根因；解除一个不清除其他。相同观察幂等，反复扫描不制造无限重复事件。恢复必须证明固定内容/能力重新可用且重新验证通过，并由人对当前包确认；工具兼容性适配或来源新内容形成新候选版本，不能把旧发布的摘要换成新值。

新版遵循完整独立验证、审阅和发布事务。发布时再次检查来源、工具和依赖闭包，保存精确 release IDs。旧版本撤回是独立操作；新版本发布不自动恢复或批准旧版本。依赖者要采用新版本必须形成自己的新 revision。暂停、撤回、挑战与来源/工具失效分别展示。

## 6 接口与实现工作包

在现有 private POST 命令和 Go 同源路由上增加独立端点：`adjudication_prepare`、`adjudicate`、`challenge_resolve`、`impact_scan`、`impact_review`；详情增加只读 `governance` 投影。发布仍走 `review_prepare`/`publish`，不能通过新接口绕过它。具体 JSON schema、大小上限和不合法组合由对应契约测试先冻结；不得直接开放通用图写入。

| 包 | 责任 | 完成条件 |
| --- | --- | --- |
| 42-A1 | Python 证据、裁决与覆盖的纯领域合同 | 真实错误/合理停止/未知不混淆，证据不足与范围外不贡献覆盖 |
| 42-A2 | Neo4j 追加记录、审阅包和发布资格投影 | 并发、幂等、旧包失效、不可变历史和项目隔离的真实存储测试 |

| 42-A4 | 新范围内任务与覆盖证据 | 任务资产先锁定、自检再运行；正反例和谱系审查；实际不足明确保留 |

| 42-B2 | 恢复、撤回、新版发布与准入 | 发布/变化并发互斥，旧发布不自动复活，使用前后身份固定 |
| 42-B3 | 可见服务和界面联调 | iTerm 展示服务日志；浏览器展示裁决、缺口和失效状态；真实人类决定独立于测试数据 |

实现阶段继续使用 `codex/` 分支与中文提交，Python/Go/前端分别记录提交和测试。保持 P4 清单所绑定代码字节不变；确需扩展执行器时创建新的能力版本和实验协议，不原地升级原运行。

## 7 阶段验收与进入 P5 的门槛

- **A-01** 缺凭条、最终补丁变化、自报通过、声明无事件、source/dev 重用均拒绝覆盖。
- **A-02** 同一历史 unknown 的原记录保留；合格复验和真人裁决仅解除对应原因。反例和无关缺口仍可阻断。
- **A-03** 人工合理停止记为任务解决而非修复；分支证据要分别满足适用条件、动作和验收。
- **A-04** viewer/editor 无裁决权；跨项目、陈旧包、重复 ID 不同正文、并发挑战均不能绕过事务。
- **A-05** 真实候选展示 22 分支的覆盖/待补清单，每项链接证据。无证据不填通过。
- **B-01** 来源变更和工具参数/行为变更分别可检测；故障和内容变化不混淆；观察不可用时拒绝新加载。
- **B-02** 必选依赖反向传播，关联边不传播；多根因逐一解除，循环/缺失/跨项目拒绝。
- **B-03** 发布与新影响并发时不能得到带陈旧资格的可加载发布；结束后准入变化保留在反馈。
- **B-04** 恢复与新版发布均需要当前固定包的人类判断，替代关系不能自动修复依赖。
- **P5 入口** 上述实现和实际存储/服务验证完成；真实候选所需独立证据与真人裁决齐全。仍有缺口时可演示拒绝和待审流程，但必须标明不具备实际发布资格。

## 9 42-A1/A2/A3 实施记录

已实现纯领域合同、Neo4j 追加记录和资格投影、宿主工件核验、Go 管理授权及浏览器裁决表单。数据面分支 `codex/skill-prototype-governance` 基于 P4.1 验收提交；控制面与前端分别使用 `codex/skill-prototype-governance-be`、`codex/skill-prototype-governance-fe`。开发合同先于实现提交，尚未推送或合并。

宿主入口为 `python -m memos.skill_governance import-evidence --registry /private/registry.json`。注册表必须为私有文件，明确限定项目、候选版本、validation ID、运行目录、原报告摘要和可选的同补丁复验。先验证全部条目再开始追加；中断后以固定操作 ID 重入。导入只登记事实，不调用模型、不创建人工判断、不发布。每份证据还绑定 `host-review-1` 的实现摘要，生成器变化需要重采集并重新准备裁决包。

采集器重新核验原凭条、当前最终快照、控制目录固定导出、原生加载事件和完整事件链；H4 的新协议复验必须对应同一最终补丁。H6 仅豁免任务明确登记的 `diagnosis.json`，其他行为文件改变不能被当作未修改的合理停止。前端使用事件的脱敏展示内容，凭条 URI 与宿主路径不公开。人类裁决绑定固定包、会话 actor、来源水位和状态序号；纠错需要显式 supersedes，陈旧包不会自动重试。

实际工件已核验并向真实项目追加登记 11 条历史 Validation 的事实：P3 最早三条仍缺采集/加载证据，第四条完整；P4 七条采集/加载完整，H4 为原 error 与事后 passed，H6 为 needs_review 且行为文件未改。事实导入未创建人工裁决，后续两项用户确认见第 10 节。所有旧任务的 `branchCandidates` 为空，现有工件不贡献 22 个专用分支；新的范围内任务按 [42-A4 合同](skill-prototype-branch-validation.md) 实现。

验证：数据面 120 项管理测试通过，其中 Neo4j 事务测试连接实际隔离测试命名空间；Go `make check` 通过（lint、vet、race、契约与构建）；前端 `pnpm verify` 通过，29 个测试文件、152 项测试，类型、lint、格式、辅助自检及构建均通过。浏览器发现深色主题表单背景问题，修复后再次检查页面、格式与构建。发布构建仍有既有大 chunk 提示。没有重新安装依赖或修改冻结的 P4/P4.1 执行器。

运行约束：旧管理服务不识别新增记录类别，必须先停止旧服务，再登记事实并启动新版。启动器在写入前检查所需端口。用户在端口检查失败后明确取消必须在 iTerm 启动的限制；本轮识别并正常关闭旧控制台启动器后，由终端启动新版，Memory 和 Docker 服务保持。前端仍在可见 Chrome 验证。旧 0.2 凭条的初始资产摘要包含文件权限，回读环境需保持原 `umask 022`；私有注册表与工件目录分别显式设为 0600/0700，不能通过忽略权限差异让旧凭条匹配。

待完成：旧 P3 三项证据不足记录的处置、42-A4 全部分支任务与实际覆盖判断，以及全部 42-B 影响传播与恢复/新版发布。当前不具备 P5 入口资格，也没有把合成测试裁决算作真人发布证据。
