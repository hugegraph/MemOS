未知结果保留在分母；人工项全部保持 pending/null，除非另有明确人类审阅。费用是模型报告值，不等于核对后的实际账单。耗时取执行器记录的 Claude 进程阶段，不含前期提炼、外部验收和人工审阅；成功子集与全部执行分别汇总。21 个单元是七任务的三组配对，不能被描述为 21 个独立任务。一次固定顺序执行不能排除模型随机性、服务负载、缓存及顺序效应。

### 3.1 已确认的验收执行器问题

H4 的外部 `fixture_isolation` 检查需要启动四个独立 pytest 子进程，现有固定验收 profile 含 `(deny process-fork)`，两者不兼容。独立临时探针已确认：同一沙箱内创建临时目录和写文件成功，但 `subprocess.run` 在 `_fork_exec` 抛 `PermissionError(errno=1)`。这是执行器限制，不是候选补丁错误的证明。

按冻结协议，本轮 H4 的完整采集和凭条绑定仍保留，行为结论为 unknown，不能从分母删除或冒充调用前基础设施无效；其实际耗时和费用计入全部执行。H4 不支持三组质量或收益比较。修正必须形成新的验收执行器和实验身份，保持 Agent 的隐藏评测隔离及网络限制，并先对全部七个任务运行真实隔离资产自检，不能观察结果后修改当前实验的验收条件。

独立的事后兼容探针进一步确认，只允许子进程仍不够：原 pytest harness 会向祖先目录收集配置。最小有效探针同时限定 `--rootdir` 与 `--confcutdir` 为本次临时测试目录；未增加 `/private`、`/dev` 或其他隐藏目录的读取授权。初始故障 failed、reference passed、unsafe failed，实际 Skill 最终补丁的副本 passed；隐藏文件读取、候选写入与网络访问仍在子进程中被拒绝。原正式报告、receipt 和最终快照 SHA 均未改变，新增模型调用为零。

这份 `posthoc compatibility probe` 只证明修正方向可行，不是原执行器的通过凭条，也不增加独立样本或改写 H4 结果。工程缺口仍需正式实现：版本化受信执行器、检查代理与 pytest harness，补齐全部七任务的隔离初始/reference/unsafe 自检，以及子进程资源上限、取消与隐藏访问测试。当前 P4 工程验收因此有保留项，不能宣称七种任务都已具备完整自动验收能力。

## 4 发布和后续边界

当前候选未发布。历史 P3 四次执行及三条未知继续归属旧版本，既不删除，也不作为新候选的独立验证。修订解决了来源约束下的三个文字与流程问题，但人类仍需判断语义、分支支持和适用范围。

下一步按依赖顺序推进：

1. **P4.1 先补执行器兼容**：正式实现上述受信子进程/pytest 收集边界，锁定新执行器和 harness 身份；先完成七任务隔离资产自检及失败路径，再以新身份复验。保留本轮三条 H4 unknown；事后复验不冒充新独立样本。
2. **补齐人工裁决与覆盖证据**：H6 停止理由、规则实际使用、来源语义支持、适用范围与分支覆盖都未获人工确认。当前六条规则限定于 MemOS 特定合同，不能仅凭其他 Python 任务的修复通过宣称已获得通用 mock/fixture 能力。若扩展规则，需要新的来源任务与未用于修订的验证任务。
3. **再完成 P5 演进闭环**：来源或工具合同变化的影响定位、暂停/撤回、固定必选依赖的失效传播、新版本重新验证及人工发布演示。`RELATED_TO` 不传播阻断；恢复单一原因不得清除其他阻断。已加载旧 Skill 的上下文无法远程抹除，应明确控制后续加载与可控制动作的能力边界。

浏览器已显示 21/21、七条新候选独立验证记录、旧候选四条历史记录，以及 `normal 加载被拒绝 / release_unavailable`。新候选当前的发布阻断原因包括待审挑战、未知验证、必需分支/边界/范围覆盖不足。服务继续运行在用户 iTerm，页面保留为可见结果；未提交人工批准或发布操作。
